Which number to trust

Primary (report)
SLA capacity on the production-faithful replay (v2): the highest load k (merged session buckets of real M3.1 traffic) whose every minute meets TTFT p50 ≤ 1.0 s, p99 ≤ 15 s, decode ≥ 60 tok/s, errors < 0.1%, reported as TPM per GPU next to production's 24 h peak. Until v2 lands, the interim number is the v1 staircase (strict rule p50 ≤ 1.6 s, p99 ≤ 22 s).
Secondary
Closed-loop saturation on real prompts (c128 / c256 / c384), always on a trace window nothing else has replayed. A ceiling without an SLA.
Appendix (north star)
Static frame: 80k cached prefix / 128 new / 600 output, the M3 manual's TPM test behind the 7 M/GPU claim. Random text, so spec decode shows no gain; one shared prefix, so it rewards load balancing and tokenizer throughput, not cache affinity.
Why they rank layouts differently
The static test rewards raw concurrency with a load-balanced router; real traffic rewards cache affinity and low prefill stall. The same 4×tp2 layout wins both once the router matches the test; production's strict-affinity policy (affinity only on high overlap, else load) serves both at once.

The methods differ a lot on the same node: 7.8 M/GPU static vs 1.7 M/GPU closed loop vs about 1 M/GPU at the strict SLA on real traffic. The gap is not error: static requests are fully cached and identical, while real requests carry 5–60k uncached tokens each. v2 is the method we will report; v1 stays only to compare against earlier runs.

Eval protocol v2: fair, production-faithful (traces built; first run armed)

  1. Workload = real M3.1 production traffic. M3.1 hub access logs from S3 (both load balancers, 5-minute parts). Measured window = the 24 h peak hour, 09-28 16:00–17:00 UTC; the 4 hours before it are warm-up. Same model era, prompts, tools and output lengths as production.
  2. Unit = one production node. Sessions (prompt_cache_key) hashed into 48 half-node buckets; two buckets = what one of the 24 nodes serves (whole sessions, real timestamps). Production's own per-request cached tokens and TTFT kept for comparison.
  3. Cache state = steady state. Every level starts from an empty cache (flush, host cache included) and rebuilds production's cache state: the last turn of every session active in the hour before the window is prefilled (max_tokens=1) in time order, then its logged next message is primed, so a radix/LRU cache holds each session's latest prefix in production's recency order. During the window each response is followed by priming with the logged next message (max_tokens=1), so later turns hit as they did in production; primes are excluded from TPM. HiCache on, as in production.
  4. Fidelity fixes. Gateway drops null-valued tool-schema keywords (production accepts a tool with "maximum": null; our engine rejected 41 of 2,317 warm-up requests). Logged image bytes are redacted to /base64/: replace with a synthetic image of similar size. Every other request replays byte-for-byte.
  5. Validity gate before any number. At 1×, per-request cache hit within ~2 points of production's (96%) and TTFT distribution within 2× of production's for the same requests; report the miss breakdown (first-seen / divergence / eviction).
  6. Load scaled by users, at real time. k× = 2k half-node session buckets merged at their real timestamps, never time compression. Sessions are causal: a turn waits for our answer to its previous turn plus the client's logged think time (a client cannot send turn n+1 before it has turn n). Ladder 1×, 2×, 3×, 4×; window 16:00–16:30 UTC (the peak), per-minute verdicts.
  7. SLA clamp, every minute. TTFT p50 ≤ 1.0 s, TTFT p99 ≤ 15 s, per-stream decode p50 ≥ 60 tok/s, errors < 0.1% (production at its peak: 0.35 s, 10.2 s, 100 tok/s, 0.06%).
  8. What the report shows. Primary: SLA capacity = highest passing k, as TPM per GPU, next to production's 24 h peak (3.38 M/GPU). Secondary: closed-loop saturation on a disjoint window (never on prompts already replayed). Appendix: static frame. Each headline run twice to show noise.

Where we are

The north star is 7 M TPM per GPU on real traffic at a strict per-minute SLA, and production is already close to it. Read-only engine counters on two production nodes (Sep 30, 13:29–13:34 PDT) show 50–53 M TPM per node = 6.3–6.6 M per GPU at engine TTFT p50 0.22–0.25 s. All 96 workers are active, so the fleet runs ≈ 1.2–1.3 B TPM; your ~1.5 B peak (≈ 7.8 M per GPU) fits. The hub logs our test is built from show only 836 M for the same minutes (4.35 M per GPU): the engines see 1.1× the requests and 1.45× the prompt tokens, so the S3 bucket misses part of the load (another entry point or uneven routing). Either way the earlier production cards (3.38 M) were too low. Our best setup holds the SLA only to ≈ 1.3 M per GPU (TTFT floor 0.9 s vs production 0.25–0.31 s), a gap of about 5×. Production's serve config explains most of it: the same model family (MXFP8 dense + NVFP4 experts + sparse Q8KV4) on TP2/EP2 with DP attention off, DFlash2 block-4 drafting, chunk 16384, 128 running per worker, HiCache 3.0, plus ~18 in-house kernels (KV4 attention v2, prefill sparse attention v3, fused verify attention, fused router, fast TP2 comm, bounded SWA draft rings) and SLO-based admission. Our engine runs the vendor's training-compatible attention path (no MSA). Next: the settings we can copy (DP attention off), the idle TTFT anatomy and step profile (chain31), then the kernel gap.

What the setups and tests mean

Vendor demo as shipped
MiniMax's 09-27 demo doc §3.2 launched exactly as written: their 09-27 engine (commit 024129fb), tp8/ep8/dp8, DSpark block 7, HiCache 192 GB, training-matched numerics. On that build the numerics flag forces DSpark to run without CUDA graphs ("eager"), so decode is 13–42 tok/s per stream.
Vendor verbatim + kernel patch
MiniMax's 09-27 demo doc §3.2 launch run exactly as written (tp8/ep8/dp8, DSpark block 7, HiCache 192 GB, training-matched numerics, 1 tokenizer worker), plus our Triton kernel patch. Same slow DSpark as the unpatched launch because the build disables CUDA graphs for DSpark in this mode.
Plain + HiCache
The 09-27 engine with DSpark switched off (normal decode, which keeps its CUDA graphs) and HiCache on. Today's highest static-frame number once the frontend was fixed, but slow per stream.
8 tokenizer workers
The frontend fix: the engine's single HTTP/tokenizer process encoded each 80k prompt twice and admitted ~2 requests/s. Eight worker processes lift that.
Old fork + DSpark graphs
The winning setup above: MiniMax's earlier 09-22 engine plus our DSpark port, which keeps CUDA graphs and therefore real spec-decode speed.
Static frame
The M3 supplier manual's TPM test: one 80k-token prefix cached, 128 new tokens, 600 output tokens, random-token text. Because the text is random, spec decode accepts almost nothing there; it understates DSpark.
Route B (real traffic)
Replay of the production access log (real prompts, sessions, images, streaming flags) with the real arrival times. 1× = one node's share of production traffic at real speed; 2× = the same requests sent twice as fast (double the load); 4× = four times.
Staircase (longitudinal)
Route B held at 1×, 2×, 4×, 6×, 8× of a node's share for 5 minutes each after warming the caches with the preceding 30 minutes; the level where TTFT or errors break is the node's real-traffic capacity.
