Where we are

Where we are, in one breath: the vendor's demo as shipped did 0.72 M TPM per GPU. Two fixes (a Triton recompile patch and 8 tokenizer workers) and one swap (the older engine build that keeps DSpark on CUDA graphs) took the node to 3.20 M per GPU on the manual's static frame; the production-shaped 4×tp2 layout under a KV router nudged that to 3.34 M (48% of the north star) and decodes 2.8× faster per stream on real traffic. On real traffic both layouts still knee at about 2.5 req/s (≈ 1 M per GPU sustained) because cold prefill dominates: the single engine keeps 91% cache hits, the 4-worker layout only 60%. Routing affinity is the next lever.

Same trace both runs (2,939 requests, 100% success on tp2, 1 timeout on tp8). The 4×tp2 layout decodes far faster per stream and wins the static frame (c64 2.52 M/GPU at TTFT 1.25 s, c128 3.34 M) but its cache-hit rate on real traffic was 59.7% vs 90.9% on the single engine: sessions were spread over four separate caches, so it paid more cold prefill and its TTFT was worse at 1×–2×. Routing affinity (prompt_cache_key passthrough / KV-event routing) is the next fix; with production-level cache hits (98.9%) the tp2 layout should pull ahead on both axes.

Trace: one node's share (1/24, sessions kept together) of 2026-09-18 11:05–11:15 UTC, 727 requests, engines started cold. The DSpark engine's 106 s TTFT is queueing: its max running requests is 128 (the CUDA-graph envelope) and cold prefills of 50–650k prompts in 8k chunks stall decode across the DP lockstep, so slots are held for minutes and arrivals wait. Production sees 98.9% cache hits because sessions continue; a cold replay does not. The staircase warms the caches with the preceding 30 minutes first, which is the fair measurement.

What the setups and tests mean

Vendor demo as shipped
MiniMax's 09-27 demo doc §3.2 launched exactly as written: their 09-27 engine (commit 024129fb), tp8/ep8/dp8, DSpark block 7, HiCache 192 GB, training-matched numerics. On that build the numerics flag forces DSpark to run without CUDA graphs ("eager"), so decode is 13–42 tok/s per stream.
Vendor verbatim + kernel patch
The same launch with our Triton recompile fix. Same eager decode, so same ceiling.
Plain + HiCache
The 09-27 engine with DSpark switched off (normal decode, which keeps its CUDA graphs) and HiCache on. Today's highest static-frame number once the frontend was fixed, but slow per stream.
8 tokenizer workers
The frontend fix: the engine's single HTTP/tokenizer process encoded each 80k prompt twice and admitted ~2 requests/s. Eight worker processes lift that.
Old fork + DSpark graphs
The winning setup above: MiniMax's earlier 09-22 engine plus our DSpark port, which keeps CUDA graphs and therefore real spec-decode speed.
Static frame
The M3 supplier manual's TPM test: one 80k-token prefix cached, 128 new tokens, 600 output tokens, random-token text. Because the text is random, spec decode accepts almost nothing there; it understates DSpark.
Route B (real traffic)
Replay of the production access log (real prompts, sessions, images, streaming flags) with the real arrival times. 1× = one node's share of production traffic at real speed; 2× = the same requests sent twice as fast (double the load); 4× = four times.
Staircase (longitudinal)
Route B held at 1×, 2×, 4×, 6×, 8× of a node's share for 5 minutes each after warming the caches with the preceding 30 minutes; the level where TTFT or errors break is the node's real-traffic capacity.
