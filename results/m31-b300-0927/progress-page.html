The causes, in plain words
  • Median first token over 1 s: time outside the GPU. A warm request (prompt already cached) waits longer the longer its conversation, and longer than production at every length: under 20k tokens 0.39 vs 0.23 s (+0.16); 20–60k 0.54 vs 0.26 (+0.28); 60–120k 0.87 vs 0.31 (+0.56); 120–250k 1.34 vs 0.48 (+0.86); above 250k 2.01 vs 0.83 (+1.18) (PROGRESS.md Oct 1 09:35). An idle test shows the same growth (Oct 1 11:15), so the extra time is outside prompt processing; templating and tokenisation are the first suspects. (PROGRESS.md Oct 1 09:35 and 11:15)
  • Generation speed under 60 tokens/s. Each engine's two GPUs step together, so prompt processing on either GPU pauses generation on both. More load means more prompt processing, so median generation speed falls: 92 tok/s at 1.79 M, 77 at 2.23 M, 57 at 3.34 M (test v3.1); 38 at 4.42 M (older test v3). (kernel profile, PROGRESS.md Oct 1 05:25)
  • Slowest 1% of first tokens over 15 s. An uncached prompt of 300k+ tokens takes 15–35 s to process and holds up its GPU pair; first tokens queued behind it miss the 15 s limit. (PROGRESS.md Oct 1 04:35 and 07:05)
  • Prompts processed again at full load. At 4.42 M we re-process 2.75× as many uncached prompt tokens as production: 84% of the extra comes from conversations whose cached prompt was evicted between turns (the largest share after 2–10 minutes idle). More cache memory (0.76, adopted Oct 1 05:52) cut those evictions. (PROGRESS.md Oct 1 03:45 and 05:55)
  • Errors at full load (older test v3). The 10 error minutes at 4.42 M came from 27 instant connection resets (the gateway's open-file limit, raised since) and 6 HTTP 500s from literal '<image>' text in prompts (fixed Oct 1 03:55). (PROGRESS.md Oct 1 03:20 and 03:55)

Full reasoning (reflections of the time)

Oct 1 09:35 · Adopted config at 1.79 M per GPU (0.375×): 13/15 minutes; TTFT 0.85 / 2.75 / 6.79 s (production on the same requests 0.34 / 2.95 / 10.4 s); decode 92 tok/s (production 67); 0 errors. At this load the tail and decode are already better than production; what fails is the median TTFT, by 20–50 ms in 2 minutes. Warm requests (< 1k new tokens) show a TTFT floor that grows with the total prompt length — 0.39 s under 20k tokens, 0.87 s at 60–120k, 1.34 s at 120–250k, 2.0 s above 250k — about 5 µs per cached token. That is not GPU math (the new tokens are few): candidates are chat-template rendering and tokenisation of the whole prompt in Python on every turn (production tokenises in Rust in its Dynamo frontend) and re-loading evicted prefixes from the host cache.

Oct 1 07:05 · 0.5× under protocol v3.1 (2.23 M per GPU): 9/15 minutes, TTFT 0.89 / 3.69 / 14.3 s, decode 77 tok/s (production 65.5), 0 errors. Median TTFT and decode beat the SLA in every minute but one; the misses are five p99 spikes in minutes that contain 300k+-token cold prompts. Those prompts need ≥ 15 s of prefill on one GPU at ~20k tok/s (production ~10 s for the same ones) and stall their whole engine meanwhile. The 0.5× knee is set by single-request prefill speed, the same bottleneck the 0.75× runs point to.

Oct 1 05:55 · Capacity (mem 0.76) at v3.1 0.75×: 1/15 again, but TTFT 1.01 / 4.84 / 18.3 s (baseline 1.19 / 6.53 / 18.2), slow first tokens −42%, extra re-prefill vs production −11%; decode 55 tok/s (baseline 53). Capacity does what the cache analysis predicted (fewer evicted sessions, lower TTFT median and p90) and stays in the config. What now fails almost every minute is decode below 60 tok/s. Both DP ranks of an engine step in lockstep through every MoE layer, so a 0.75 s prefill chunk on either rank also stalls the other rank's decode; mixing prefill and decode across ranks (speculative_skip_dp_mlp_sync) cannot help for the same reason, and overlap scheduling is already on. Decode speed at load is therefore set by how much prefill time there is.

Oct 1 05:25 · Kernel profile of the frontier engine (torch profiler, between levers): a cold 131k-token prefill takes 6.7 s on one DP rank (19.5k tok/s); decode with 32 streams keeps the GPU busy only 67–71% of the time. Prefill time on the busy rank: sparse attention 30% (_q8kv4_sparse_partial + combine), indexer 21% (_q8kv4_index_score + top-k), MoE 20%, dense MXFP8 GEMMs 13%. These Q8KV4 Triton kernels run at roughly 12–14% of tensor-core peak; production replaces exactly them with in-house kernels (kv4_prefill_attn_v3, kv4_prefill_index_v3, kv4_index_tpshard) and splits each prompt over 2 GPUs (attention TP2), so its per-request prefill is ~2–3× ours. The scheduler confirms the coupling: with speculative decoding + DP attention, prefill always runs first and the two ranks cannot mix prefill and decode, so any prefill chunk on either rank pauses decoding on both. At 0.75× each rank prefills ~15% of the time → decode paused ~28% → 74 × 0.72 ≈ 53 tok/s, which is what we measured.

Oct 1 04:35 · Load-aware pinning at v3 0.5× (2.23 M per GPU): 7/15 minutes pass (baseline routing 2/15); TTFT 0.89 / 4.23 / 18.3 s vs production 0.34 / 2.96 / 10.4; decode 74 tok/s (production 65). Median and decode are at or above production; the misses are tail spikes. Engine logs show the mechanism: a single 270–530k-token cold prompt is prefilled in 16k chunks for 20–35 s and every other request on that DP rank waits (the other rank of the engine slows too, because both step together in the MoE). Three of the five spike sources were requests production itself rejected with HTTP 429 (its admission sheds big cold prompts under pressure); our replay was serving them. Two failing minutes were only the six media-tag errors, now fixed.

Oct 1 03:55 · Root cause of the recurring 6 HTTP 500s (and one HTTP 400) on real traffic v3: the engine's multimodal loader treats literal '<image>' / '<video>' in user text as media slots. One v3 session carries 6 literal '<image>' strings plus real images → 'More IMAGE tokens found than data provided' → 500; another has HTML '<video>' tags → 400. Production answers both with 200.
