## Errors
- E1 (key claim). "134 NCCL ring-LL collectives" and "All 134 calls are RING_LL today [measured]" are not measured. The kernel name does not show the protocol. NCCL 2.28.9 gives every AllGather kernel the entry name ncclDevKernel_AllGather_RING_LL, and every bf16-sum ReduceScatter kernel the name ..._Sum_bf16_RING_LL, whatever protocol runs [code: NCCL src/device/generate.py:145-151 best_kernel, :293-313 ncclDevKernelForFunc]. The block size does show it. At 56 running, all 134 calls have 544 threads, which is ring SIMPLE (512 threads plus 1 sync warp). At 32 running, all 134 have 512 threads, which is ring LL [measured: g2/collectives-skeptic/out_coll_grid_proto.txt; code: NCCL graph/tuning.cc:230-243, enqueue.cc topoGetAlgoInfo 'SIMPLE && RING -> nt += WARP_SIZE', include/device.h:90-92,109]. Nothing sets the protocol: EXTRA_ENV, the image ENV and the fork set no NCCL_* variable (the fork sets NCCL_ALGO only for deterministic inference, which is off) [measured; code: server_args.py:7890].
- E2 (key claim). The Option A estimate is not supported: -1.5..-2.1 ms at 56 running, -0.5..-1.1 ms at 32, ranked 'cheapest' and 'run first'. At 56 running the calls already use Simple, so NCCL_PROTO=Simple changes nothing. With NCCL_PROTO=LL128,Simple the NCCL model still picks Simple at both sizes: ring LL128 has 4.1 us more latency (15.9 vs 11.8 us) and 0.92x the bandwidth [code: NCCL tuning.cc:143-166, :304-305]. At 32 running both arms replace LL with Simple. Measured Simple costs 32.7 us per call at 5.5 MB; LL costs 21.6 us at 3.15 MB. A loss at 32 is therefore more likely than a gain [inferred, LOW-MED].
- E3. The Option A gate cannot pass: "profile kernel names change to ..._RING_SIMPLE or ..._RING_LL128". The names never change (see E1). Also, the log line 'NCCL_PROTO set by environment' only proves that NCCL read the variable. It does not show which protocol each call uses.
- E4. 'NCCL mis-tune: the choice of LL is a mis-tune on B300' and the 'ring-LL 9.4 us/MB + 7 us fit (~106 GB/s)' are not supported. The two fit points use different protocols: LL at 32 running, Simple at 56. For a 2-rank AG/RS, NCCL's own model switches from LL to Simple between 3.15 MB and 5.5 MB total, for any ring bus bandwidth of about 0.6-1.6 TB/s. This matches the measured block sizes. Both protocols run 1.7-2.3x slower than the model: LL 21.6 us vs about 12.8 us, Simple 32.7 us vs about 14.5 us [code: tuning.cc constants; inferred, MED].
- E5. The Option B gate is wrong: "Prefill chunks above 16 MB stay on NCCL". At world size 2, ca_comm.should_custom_ar() returns true up to 128 MB. In graphs the limits are 1-shot push <= 8 MB, 1-shot pull <= 32 MB and 2-shot pull <= 128 MB. In eager mode they are 16, 128 and 128 MB [code: srt/distributed/device_communicators/configs/custom_all_reduce_v2.py:115-136; custom_all_reduce_v2.py:307-336]. As specified, B moves every 8-128 MB prefill AG/RS (breakable graphs and eager) onto all-reduce emulation. The AG then moves 2x the bytes, plus a fill and a copy. A prefill/TTFT loss is likely [inferred, MED].
- E6 (citation). "The JIT drops --use_fast_math [jit/utils/compile.py:247-250]" is wrong. That branch runs only when torch.version.hip is set (ROCm). On CUDA the flag is never added. The defaults are the arch flag, -std=c++20, -O3 and --expt-relaxed-constexpr [code: python/sglang/kernels/jit/utils/arch.py:129-137], and the CAR v2 loader passes no extra flags [code: python/sglang/kernels/ops/communication/all_reduce.py:141-149]. The conclusion still holds: no FTZ, and one rounding.
- E7 (safety gap in the plan). The Section 6 microbench ('no engine, 10-15 GPU minutes') and the B gates (torch.equal on recorded batches, greedy 30/30) name no device binding, no g67/HOLD and no GPU lock. The report itself ran nothing on GPUs: its helper scripts are CPU-only [code read].

## Corrected
- Inventory: one TP2 verify step holds 134 NCCL ring collectives: target 64 AG + 60 RS, draft 5 AG + 5 RS. All run inside CUDA graphs. They take 4.58 ms busy (94% alone) at 56 running and 3.13 ms (92% alone) at 32 [measured, reproduced exactly]. The protocol comes from the block size: ring SIMPLE (544 threads) at 56 running and ring LL (512 threads) at 32 [measured: out_coll_grid_proto.txt; code: NCCL tuning.cc/enqueue.cc/device.h].
- Do not use the 9.4 us/MB 'ring-LL' fit or the 'LL mis-tune' argument. Use the measured per-call times instead. At 56 running (Simple): AG 32.7 us, RS 31.3 us, draft 34.2/30.8 us. At 32 running (LL): AG 21.6 us, RS 22.1 us, draft 21.3/20.6 us [measured].
- Option A: expect about 0 ms at 56 running, because the calls already use Simple. Expect 0..+1 ms (worse) at 32 running, where LL becomes Simple. NCCL_PROTO=LL128,Simple behaves like NCCL_PROTO=Simple, because the model never prefers ring LL128 over Simple [code: tuning.cc]. Remove A from the engine queue. Run a forced NCCL_PROTO=LL128 probe, and Simple at 1.57 MB/rank, only inside the microbench [inferred, LOW-MED].
- A protocol gate must check the NCCL block size, not the kernel name: 512 = LL, 544 = ring SIMPLE, 640 = LL128 (valid while NCCL_NTHREADS and NCCL_LL128_NTHREADS are unset). The fixed g2/collectives/coll_grid.py prints this. Alternatively, read the NCCL_DEBUG=INFO NCCL_DEBUG_SUBSYS=TUNING table.
- Option B: add an explicit size cap to the gate, nbytes <= 8 MB (the graph 1-shot push threshold). That covers every decode/verify shape up to bs 64 (6.3 MB at 512 tokens). Alternatively, limit B to decode/target-verify forward modes. Keep NCCL for prefill. The B savings estimates still hold, because they are anchored on measured per-call times: -2.2..-2.6 ms at 56 running and -1.4..-1.75 ms at 32 [arithmetic re-checked].
- Ranking after the corrections. Best gain per day: B with the 8 MB cap (0.5-1 day). Best gain: C, -2.8..-3.3 ms at 56 (2-3 days). Add-on: D (logits AG 4 -> 32 CTAs, -0.42..-0.48 ms, helps DP2 too). Reject: E (--enable-symm-mem flag only). Drop: A. No gain: torch symm mem, pymscclpp, FlashInfer/k3 AR fusion, CAR v2 knobs.
- G2 core finding (confirmed). With --enable-symm-mem only 66 calls qualify for NCCL symmetric kernels: 60 target RS + 5 draft RS (in place on the pooled o_proj output) and 1 draft AG (the final _gather of the pooled down_proj output). The other 68 AGs stay on the ring path. The reason: NCCL 2.28.9 needs both send and recv windows, and their inputs (training-RMSNorm torch.empty, residual_output, MoE output) are outside the pool [code: NCCL scheduler/symmetric_sched.cc:30, enqueue.cc:2580; training_rmsnorm.py:24-35,:50-64; linear.py:1583-1589; communicator.py:1192-1210, :981-990, :532-545]. The flag also turns SHX off [minimax_m3_shx.py:198-199]. The two embedding ARs move to pynccl, because SGLANG_ENABLE_CUSTOM_ALL_REDUCE_V2_MULTINODE defaults to False [environ.py:896; parallel_state.py:703-718]. The C-13 output-buffer blocker is not real in decode/verify graphs [decode_cuda_graph_runner.py:804,:973-977]. The SGLANG_DEBUG_SYMM_MEM check sees only the AG output [parallel_state.py:1181-1182].
- Numerics: CAR v2 is bit-exact with NCCL at TP2. CAR v2 accumulates in fp32 starting from the first operand and does one RNE cast [custom_all_reduce.cuh:97-115; sgl_kernel/type.cuh:166]. It is built without fast-math, because the CUDA JIT defaults never add it [jit/utils/arch.py:129-137]. NCCL symmetric RS also accumulates from the first operand [NCCL symmetric/reduce_scatter.cuh:37-86]. An independent pure-Python check found 0 mismatches over 600,000 pairs, including 40,770 subnormal-range sums. AG padding: -0.0 gives 0 mismatches, +0.0 gives 1 (input 0x8000) [measured: g2/collectives-skeptic/out_numerics_purepy.txt]. This closes the report's untested-subnormal caveat.
- Safety for every GPU follow-up (A/B/D gates, microbench). Run only on GPUs 6,7: through the pinned launcher or run_tp2prof.sh (--gpus device=6,7), or in a container with --gpus '"device=6,7"'.
